# Development

## Baseline

First Torch targets Minecraft 26.1.2 on NeoForge 26.1.2.84. Dependency versions and CurseForge file IDs are pinned in `manifest.json`.

The repository also contains the initial native NeoForge mod foundation for the 0.13.0 migration. It uses ModDevGradle and Java 25 and intentionally runs without FTB dependencies. The existing pack remains unchanged as the authoritative curriculum and migration source until the native runtime reaches feature parity.

The current pack deliberately uses the FTB quest stack plus FTB Filter System and FTB XMod Compat for flexible vanilla item objectives. Initially provides exactly one Quest Book per player on first entry; its configuration is limited to `ftbquests:book` in hotbar slot 8. KubeJS was removed after its required Better Advanced Tooltips dependency caused a startup Mixin failure. Add scripting only when the curriculum requires it and the full dependency chain has passed a clean-profile startup test.

FTB Quests 26.1+ stores quest definitions and translations as JSON5. Legacy `.snbt` examples are not valid guidance for this project.

The quest book sets `pause_game: true` so the integrated single-player world pauses while a learner reads. Dedicated multiplayer servers and worlds opened to LAN continue running; the Welcome chapter states that distinction explicitly.

## Repository layout

- `build.gradle`, `settings.gradle`, and `gradle.properties`: native NeoForge mod build
- `src/main/java/`: native mod source code
- `src/main/resources/`: native mod assets and translations
- `src/main/templates/`: generated NeoForge metadata templates
- `.run/`: shared IntelliJ IDEA Gradle run configurations
- `manifest.json`: CurseForge pack metadata and dependency pins
- `overrides/config/ftbquests/quests/`: version-controlled quest book
- `overrides/config/initially/`: one-time starter Quest Book configuration
- `docs/`: curriculum, development rules, and roadmap
- `tools/`: local and CI validation/build scripts
- `build/`: generated import archives; ignored by Git

Player progress belongs to a world or server instance and must never be copied into this repository.

### Native guide data boundary

Native guide definitions live under `data/firsttorch/guides/*.json` in server datapacks; the bundled alpha schema example is stored at `src/main/resources/data/firsttorch/guides/`. On each server resource reload, First Torch sorts matching resources by path, parses them with path-aware diagnostics, validates the complete guide set, and atomically publishes an immutable server snapshot only after every resource succeeds. A failed reload therefore leaves the previously published snapshot untouched.

NeoForge play networking synchronises validated definitions and the executing player's live progress on login and datapack reload. Progress changes are sent after server evaluation, including manual confirmations; unchanged observations are not repeatedly transmitted. Both payloads are versioned and bounded. Disconnecting clears both client caches, and a definition reload clears the prior progress until its replacement arrives. Storage or transport failure publishes an unavailable state rather than stale progress. The native screen opens in live mode with server-supplied badges, prerequisite locks and task counts. The independent design preview remains optional and never changes player data.

### Local test completion

The shared IntelliJ First Torch Client (`runClient`) enables JVM property `firsttorch.testMode=true`. Only the integrated world's owning player can use the `TEST: Complete` browser button or `/firsttorch test_complete <quest-id>`; guests and dedicated servers cannot use this bypass. Normal mod launches have no test property and register no such command. It completes the selected quest's transitive prerequisite closure and every associated objective, preserving unrelated and historical progress. It does not grant vanilla advancements, spawn items, or alter reward claims: rewards still use the ordinary claim path. Test completion persists with the world's progress and is not undone when test mode is disabled. Use a disposable test world. To test the normal client, remove/disable this development run property; no key bindings or existing world data are rewritten on startup.

Tasks may declare an optional `titleKey` for their individual bilingual objective label. Omitted labels keep the previous item/tag/manual fallback. Protocol 9 includes these labels. The bundled task audit distinguishes inventory possession from practical confirmation: pure item/tag objectives remain automatic; the Shovel, Axe and Chest lessons each combine automatic possession with a separately named manual exercise. The interface must never describe those exercises merely as a generic confirmation. IDs, task types and stored completions are retained. An optional quest `image` contains `resource`, pixel `width` and `height`, and a bilingual `altKey`. Images refer to local resource-pack PNGs, never URLs or filesystem paths. Ten illustrations reuse the original PNGs from the retained pack through a narrowly scoped Gradle resource inclusion; their binaries are not duplicated or modified. The renderer preserves the declared aspect ratio and includes the image in the detail pane's scrolling and scissor area. Its caption is always visible and included in quest narration; unavailable images retain that description with a brief notice. Datapack definitions alone do not distribute textures: a corresponding client resource pack is required for additional images. Full-size viewing and multiple interleaved images are not implemented yet. Client and server must both use network protocol 9.

Chapters and quests may set `iconItemId` to a lowercase namespaced item identifier (maximum 256 characters). It is cosmetic only, uses the target game's item renderer and never changes task requirements. Chapters without an icon show Book; omitted quest icons retain the first inventory-task item or Book fallback; unavailable items and Air render as Book. Protocol 9 requires matching updated client and server versions. Check a completed and a locked quest in both map and detail view after restarting; badges must remain visible over the original item icons.

Native quests may additionally define `tasks` and `rewards` arrays; omitted arrays remain empty for existing schema-1 guides. Each array is limited to 32 entries. Every nested entry has its own globally unique stable ID, including across guides.

- Task: `{"id":"3000000000000001","type":"INVENTORY","itemId":"minecraft:oak_log","count":8}`. Inventory counts are 1–4096. `MANUAL` tasks use count 1 and omit itemId.
- Tagged inventory task: `INVENTORY_TAG` uses `itemId` as an item-tag identifier, for example `minecraft:planks`, without a leading `#`. Different matching stacks are summed using the server's current tags. Internal observation keys use `#minecraft:planks` to keep groups distinct from exact item IDs. Only tags referenced by loaded tasks are counted; unknown/empty tags contribute zero. Quantities are bounded to 4096 and completion remains sticky. The client shows a translated group label and the quest's original item icon.
- Reward: `{"id":"4000000000000001","type":"EXPERIENCE","amount":15}`. Experience amounts are exact points, bounded 1–10000, never levels. `ITEM` rewards require a namespaced itemId and amount 1–4096.

Definitions are immutable and validated on resource loading and after network decoding. Network protocol 9 additionally carries optional chapter and quest item icons alongside task/reward definitions, player progress and reward-claim states, so both client and server need the updated mod. Item IDs are validated syntactically; unknown registry IDs cannot match a real inventory item and are rejected during payout.

The server now evaluates inventory and advancement tasks once every 20 player ticks and accepts explicit manual confirmations through the alpha commands below. Empty tasks do not imply automatic completion. Existing client-only design fixtures remain separate. Task labels describe each individual objective; location objectives remain follow-up work.

### Reward claiming and recovery

A completed quest's fixed reward batch can be claimed once. The server rechecks completion and prerequisites, validates item registry entries, plans the entire batch into copies of the 36 main inventory slots, and checks total XP overflow. A full inventory rejects the batch before anything is reserved or paid; equipment slots and dropped entities are not used as overflow storage.

Before changing XP or inventory, a per-player, per-quest reservation is written with CREATE_NEW and forced to disk under `data/firsttorch/reward_claims/<playerUUID>/<questId>.claim`. Completion writes a separate CREATE_NEW, forced `.complete` record with matching rewards, avoiding Windows failures when atomically replacing an existing file. Legacy completed `.claim` records remain readable. Orphaned, partial or mismatched completion records fail closed. Existing reservations and completed claims both prevent retry, including when rewards are later edited under the same quest ID. The journal is bounded, strictly validated, and corrupted files are never deleted or replaced by an empty state. Reward-storage failure blocks payouts but preserves synchronised quest progress and lesson actions; unclaimed rewards are shown as pending review.

This is conservative at-most-once payout, not an atomic transaction across the journal and Minecraft player data. A process crash or disk failure during payout can leave a partial or lost reward, including a completed journal whose player data was not yet saved. Pending claims require manual review; they are never automatically paid again. File force cannot guarantee survival against every filesystem or power failure. Back up and restore the entire world, including player data, progress and claim journals together. Do not delete a journal just to re-enable its button.

## Build and validate

```powershell
./gradlew.bat build
pwsh ./tools/validate-pack.ps1
pwsh ./tools/build-pack.ps1
```

The Gradle build creates the independent mod JAR under `build/libs/`. The pack commands continue to validate and build the unchanged FTB-based migration source.

The pack build creates `build/First-Torch-<version>.zip`. Import the archive into a compatible launcher; the launcher downloads the pinned mods.

For integration into an existing compatible profile, run `pwsh ./tools/build-quest-overlay.ps1`. The resulting Quest Overlay contains only the three updater-managed runtime trees and `FIRST-TORCH-INSTALL.txt`. It excludes `manifest.json`, `options.txt`, mod JARs, saves, and player progress. Existing FTB quest books and Initially configurations require a deliberate merge rather than replacement.

## Update a development instance in place

For quest and configuration iterations, close Minecraft and run:

```powershell
pwsh ./tools/update-instance.ps1 -InstancePath "C:\Games\CurseForge\Minecraft\Instances\First Torch"
```

The updater has an explicit managed-path allowlist. It backs up the current managed files under `<instance>/.first-torch/backups/<timestamp>/`, replaces only the quest book, the Initially starter-item configuration, and the First Torch guide resource pack from `overrides/`, verifies copied trees by SHA-256, and records the installed pack version in `<instance>/.first-torch/state.json`. It adds `file/first_torch_guides` to the existing `resourcePacks` option without removing other packs or changing unrelated settings.

The following stay outside updater ownership:

- `saves/`
- all `options.txt` values except adding the First Torch guide pack to `resourcePacks`
- `screenshots/`
- all resource packs except `resourcepacks/first_torch_guides/`
- logs, caches, and unrelated mod configuration

The updater does not install or remove mod JARs. If `manifest.json` changes its dependency list, update through CurseForge or perform a fresh profile import before applying overrides.
